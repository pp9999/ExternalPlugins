# ExternalPluginsMM

ExternalPluginsMM is the standalone x64 plugin project for the current
MemoryError host. It provides the host-facing SDK facade, bundled C++ scripts,
and the plugin UI/lifecycle entry points.

## Host compatibility

The declarations in `ExternalPlugins/source/API.h`, `Structs.h`, and the domain
headers mirror the public ABI exposed by the current MemoryError DLL. Keep
those headers synchronized with the host whenever exported functions or
cross-DLL structs change. The project links against the host's generated
`XInput1_4_inject.lib`; `ExternalPlugins/MemoryError.def` is only a historical
binary dump and is not the API source of truth.

The plugin exports these unmangled lifecycle functions:

- `GetScripts`
- `LoadDLL(HWND)`
- `RenderUI()`
- `onUnload()`
- `UnloadRequested()`

The host also requires `PluginName` and `PluginAuthor` version-resource fields
for discovery.

## Updating the SDK

The headers are synchronized with MemoryError master `8759e31a` (2026-10-30).
This includes the shared `AllObject`/`SPLAT` layouts, `ThreadSafeLogStream`,
`FFPOINT` parameters, current varp/varc helpers, path APIs and event readers.
`ScripCuRunning1` and `ScripCuRunning2` remain plugin-local compatibility
strings for bundled scripts; the host only exports `ScripCuRunning0`.

Check source declarations and shared types without compiling:

```text
python tools/check_host_api.py --host ../MemoryError
```

The checker compares `API.h` with the host's `MemoryError.h`, `Detours.h`
and `MemoryReadFun.h`, and checks shared types and domain headers. It does
not validate a compiled DLL or import library.

The bundled `ExternalPlugins/libs/XInput1_4_inject.lib` was copied from
`MemoryError/x64/Build_DLL` on 2026-10-30. Its companion DLL has PE timestamp
`1793393423` (2026-10-30T20:50:23+00:00). Symbol inspection confirms the
`ThreadSafeLogStream` logging type, unsigned `GetClientCycle`, four-argument
`ReadAllObjectsArray` and both `VP_FindPSettBit` / `VC_FindPSettBit` helpers.
Every import name in the copied library exists in that companion DLL.

For future updates, replace this library with the one generated by the same
host build you intend to load. Rebuild the plugin against that host ABI;
existing plugin binaries retain their old layouts. The source check above
is not a substitute for a matching import library and a manual live test.

## Build output

The x64 post-build step copies the DLL to:

```text
%USERPROFILE%\MemoryError\Plugins\ExternalPlugins.dll
```

This matches the default plugin directory used by MemoryError. Final Visual
Studio builds and live plugin loading must be performed manually by the
developer; the repository agent must not build or inject the DLL.
